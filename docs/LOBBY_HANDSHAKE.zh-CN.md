## 玩家看到的行为

大厅左上角原连接信息的位置显示 `Acbric` 状态按钮，支持中文/英文。悬停可看原连接信息、逐玩家状态、部分差异及检查边界，点击打开**联机大厅面板**。面板内含状态与手动重新检查、各 MOD 注册的玩法设置入口（开局城市数、资金、AI 舰队等），以及 Java MOD（AcMod）与原生 MOD 的「下次启动启用/停用」。完整代码差异可继续使用离线清单比较器；入口失败的堆栈见本地启动报告。

| 状态 | 处理方式 |
| --- | --- |
| 等待连接与房间 / 等待其他玩家 | 等待连接及其他玩家进入 |
| 代码检查中 / 等待房主确认 | 等待本轮检查及房主更新完成 |
| 代码一致 | 满足原生资源、玩家选择等条件后，可以点击准备 |
| 代码不同 | 对齐游戏构建、Java 版本、框架和实际加载的 MOD，重启后再进房 |
| 无法验证 | 查看清单和启动报告，修复入口失败、无法散列或超过限额的问题 |
| 检查超时 | 检查连接及所有玩家的框架版本；框架会自动重试，也可在面板里手动重新检查 |

框架没有“忽略失败继续开始”的开关。代码一致只是一项必要条件；仍需所有玩家准备及游戏原有条件。0.3.6 起准备意愿**逐成员保留**：只有本机换了会话（重连、手动重新检查、换房）才需要重新准备；例行续证、其他成员进出房间、玩法设置更新以及房主处理地图设置、帝国选择等原生变更都不会再撤销全员的准备。原生重同步（`ResumeScreen` 重建大厅会把所有玩家的 ready 位清零，并且不拷贝 `readySent`）之后，框架会在本机此前确实点过准备、且门禁允许时自动重发一次准备，玩家不需要在大厅里重新点。

一轮检查超时后不需要玩家手动干预：框架按失败轮数退避（5/10/20/30 秒）自动开启下一轮检查，沿用同一个会话令牌，因此不会连累其他玩家的准备。规则交换同样按周期窗口自动重试，不再出现超时后永久卡住。

30 秒的例行续证期间暂时停止接收新准备，身份不变则保留准备意愿。所有当前凭据齐全的房主更新可授予最多 2 秒的开局执行窗口，减少刚好跨过续证时刻导致部分客户端留在大厅的问题。已知连接、成员、会话变化仍立即撤销对应成员的决定与开局许可；后续无效房主更新也撤销许可。这不是网络分区下的原子开局或分布式共识保证。

## 兼容和范围

- 既有公开 MOD API 与事件语义保留，旧功能 MOD 不需要为此重编译。但同房玩家必须使用相同代码及支持此检查的框架；这不承诺与旧框架混用联机。旧框架不响应时超时，不回退成功。
- 首批只适配多人战役大厅的新建和续局。单人游戏、战斗大厅没有新增代码准备门禁；全局收件入口仍会移除框架自身的保留消息，防止尾包进入战役命令解释器。
- 原生 `modsLoaded`、资源重载/失败、帝国选择和全员准备条件仍生效。框架不替代原生资源下载检查。
- 大厅面板里的 MOD 启停写入各自的启用状态，**重启后生效**：Java MOD（AcMod）经 `ModSelection` 在下次启动时过滤，原生 MOD 写游戏自己的启用设置。联机要求同房玩家加载同一组 MOD，所以面板同时列出原生列表与差异提示；不在大厅内热重载 MOD（原生热重载只覆盖原生 MOD，且会让已确认的代码清单失效）。
- 比较本进程启动时采集的[代码身份](CODE_MANIFEST.zh-CN.md)，不读取可编辑的磁盘报告来放行。热改文件或点击重试不会重新加载/重新散列 MOD；修改文件后必须重启。
- 仅比较显式声明的新战役候选或存档规则；不比较/同步完整本地配置、有效原生资源、扩展包、其他存档内容与运行状态；不提供身份认证或反作弊。相同代码仍可能产生不同状态。
- 续局世界仍可能在准备完成前构造。`LOADED` 的既有时序不变，不能假设它发生于握手通过之后。

## 接入方式与准备凭据

产品在 `AirshipGame.pollMessage` 返回处处理已消费的消息，保留其他消息的顺序、成员帧和原生房主处理路径；不额外轮询 Client。过滤保留类型 `acbric:code_handshake` 和 `acbric:campaign_rules`。当前连接、欢迎消息与实时成员帧共同确定上下文；历史帧不能确认代码或准备，重复/倒序实时帧被拒绝。

**LAN 战役可以使用房间 0**。公共聊天是否排除由欢迎信息和当前界面判断，不能仅按数字 0 排除。LAN 原生欢迎中的 `initiatorID` 固定为 0，框架房主更新补充实际玩家 ID；普通房间沿用原生 initiatorID。该字段与原生消息一样是自报信息，不是可信身份。

内部字段 `acbricLobby` 附加到原生 `strategicReady`、`strategicResumeReady`、`hosterUpdate`：

| 字段 | 约束 |
| --- | --- |
| `v`、`channel`、`host` | 当前版本 2、实际房间 ID、房主玩家 ID |
| `hostSession`、`round` | 房主上下文 UUID 及该上下文中的递增批次 |
| `sessions` | 当前全员 ID 到已验证上下文 UUID 的完整映射 |
| `rulesDigest` | 当前规则集的 SHA-256 摘要；仅在摘要变化后的 5 秒宽限窗口内继续接受上一份摘要的凭据，避免丢掉正在路上的准备 |
| `proof` | 仅准备消息：玩家实际点击准备时生成的 UUID |
| `ready` | 仅房主更新：已接受的玩家 ID 到准备 UUID 的映射 |

房主只接受匹配当前完整上下文的准备，原生裸 `ready=true` 不足以通过；客户端还须确认自己的准备凭据。成员、房主或会话改变后旧批次不能复用，但**会话未变的成员保留自己的凭据**：进房/离房只让新成员从零检查、并作废开局许可，不会让其他人重新准备。原生玩家列表必须恰好覆盖完整成员集合，收到完整有效更新后才允许原生 `canStart` 通过；实际 `sendReady`/`startGame` 方法入口也再次检查。

`Client` Mixin 观察 socket 与原生重连标志变化；不能仅依赖原生 `isConnectedRaw`，它在重连中仍可能返回真。`ResumeScreen` 可能重建大厅但不再调用 `processWelcome`，恢复钩子交接房间上下文、已表达的**准备意愿**并关闭旧会话，新大厅重新握手后自动恢复准备。

内部协议字段和 `impl` 桥接类不是稳定 MOD API。新增 `ClientConnectionMixin`、`LobbyNetworkMixin`、`StrategicLobbyMixin`，并扩展既有 `ResumeScreenMixin`，dev.9 共 19 个 Mixin，dev.10 增加生成钩子后共 20 个。状态按钮使用原生渲染位置的 Redirect；其他 MOD 修改同一调用点时仍可能冲突，应检查 Mixin 日志。

## 验证与待验收

dev.9 当时的标准构建通过 477 项无界面检查，其中 44 项新增大厅状态/准备检查。真实游戏 1.2.15.2 / 1.2.14，各以原生 Server 和两个独立 Fabric/Client 进程验证 LAN 及普通房间；最终 10 组实验共 104 项上层检查通过。覆盖重试、旧凭据、原生重连、恢复交接、准备/开局阻断和 MOD 差异/缺失/入口失败。

探针使用最小大厅/世界夹具：实际执行欢迎、收件、准备、条件方法和失败时的 startGame；成功后只验证 canStart，不生成完整世界。恢复交接通过真实变换后的 RETURN 钩子验证，没有执行恢复界面的完整流程。普通房间实验仍在本机 Server 上，线上预处理队列由探针填充，不覆盖官方服务认证。状态按钮注入目标已实际变换，完整 GUI 排版、成功开局、完整续局/恢复、跨机器/官方服务器和长期运行仍需人工验收。

当前 dev.10 验证：541 项标准断言；两版 14 轮/204 项网络检查，细节见 [规则验证范围](SHARED_RULES.zh-CN.md#验证范围)。

当前 0.3.6 验证：标准构建 16 套件 **1135 项**通过（`handshake` 134 项、`rules` 132 项，两套件合计比 0.3.5.1 新增 25 项），覆盖逐成员准备保留、会话跨成员进出保留、摘要变化保留准备与宽限窗口、超时自动重试、房主快照采用与不可采用、规则交换周期性重试窗口。以下仍需人工验收：真实游戏里的准备/开局流程、重同步后的可见准备状态、面板里的 MOD 启停实际生效、跨机器或官方服务器联机。
